---
title: Understand reactive execution
---

Notebooks run cells according to variable dependencies, not the order cells appear on the page. If cell B reads a variable defined in cell A, cell B depends on cell A. When cell A runs, the notebook can rerun cell B so that its output reflects the latest value.

A cell's *definitions* are the global names it creates, such as variables, functions, classes, and imported names. A cell's *references* are the global names it reads from other cells. Notebooks use definitions and references to determine which cells depend on each other.

For more detail, see marimo's [How marimo runs cells](https://docs.marimo.io/guides/reactivity/#how-marimo-runs-cells).

## Understand stale and blocked cells

A cell is *stale* if it hasn't run with its latest code and inputs. A cell that has never run is considered stale. After a cell runs with its current code and inputs, it is no longer stale.

A cell is *blocked* if it or one of its ancestor cells is disabled. Blocked cells do not run automatically, even if their inputs change. When the disabled cell is re-enabled, the notebook can run any blocked cells that need updated outputs.

A cell becomes stale when:

- You edit the cell's code.
- An ancestor cell runs while the notebook uses [lazy execution](/models/notebooks/configure-notebook#configure-startup-behavior). In this mode, the notebook marks dependent cells as stale instead of automatically running them.
- A Python module used by the cell changes while lazy module autoreloading is enabled.

Run a stale cell to update its output. If the cell has stale ancestors, the notebook runs those cells first. You can also run all stale cells at once.

<Info>
In-place mutations don't mark dependent cells as stale because notebooks don't track mutations to objects.
</Info>

To unblock a cell, re-enable the disabled cell that it depends on. For steps, see [Disable or enable a cell](/models/notebooks/run-notebook-cells#disable-or-enable-a-cell).

## Deleting cells

If you delete a cell, the global variables defined in that cell are also deleted. Cells that reference deleted variables are rerun, invalidated, or marked stale depending on [runtime settings](/models/notebooks/configure-notebook#configure-startup-behavior).

## Avoid multiple global variable definitions

Define each global variable in only one cell. If two cells define the same global name, the notebook can't determine a single source of truth for downstream cells. This includes functions, classes, and imported package names.

For temporary variables, [prefix the variable name with a single underscore](https://docs.marimo.io/guides/reactivity/#creating-local-variables) to make it local to that cell. You can also [define temporary variables within a function](https://docs.marimo.io/guides/reactivity/#encapsulating-code-in-functions).

For more information, see [Creating local variables](https://docs.marimo.io/guides/reactivity/#creating-temporary-variables).

## Avoid untracked object mutations

Avoid mutating objects that are used across multiple cells. Notebooks do not track mutations to objects. 

For example, if one cell adds a column to a DataFrame object defined in another cell, cells that reference the DataFrame don't automatically rerun. To keep the notebook state consistent, mutate an object in the cell that defines it or assign the updated value to a new variable.

If you need to update an object, consider creating a new object instead of modifying the existing one. 

For more information, see [Variable mutations are not tracked](https://docs.marimo.io/guides/reactivity/#variable-mutations-are-not-tracked).

## Navigate cell relationships with the minimap

Use the [Dependencies panel](https://docs.marimo.io/guides/editor_features/dataflow/#dependencies-panel) to understand relationships between cells.

1. From the sidebar, select **Explore dependencies** (<Icon icon="sitemap" iconType="solid"/>). 
2. Select **MINIMAP**.

## View the dependency graph

Use the [Graph view](https://docs.marimo.io/guides/editor_features/dataflow/#graph-view) to visualize dependencies between cells as a directed acyclic graph (DAG).

1. From the sidebar, select **Explore dependencies** (<Icon icon="sitemap" iconType="solid"/>). 
2. Select **GRAPH**.

You can zoom in and out, drag, and rearrange nodes to better understand the relationships between cells.
