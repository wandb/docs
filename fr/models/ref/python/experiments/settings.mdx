## <Badge color="yellow" size="lg" shape="rounded">Classe</Badge> wandb.Settings

Paramètres de configuration du SDK W&amp;B.

Cette classe gère les paramètres de configuration du SDK W&amp;B
et garantit la sécurité des types ainsi que la validation de tous les paramètres. Les paramètres sont accessibles
sous forme d&#39;attributs et peuvent être initialisés par programmation, via des variables
d&#39;environnement (préfixe `WANDB_`), et à l&#39;aide de fichiers de configuration.

Les paramètres sont organisés en trois catégories :

1. Paramètres publics : options de configuration principales que les utilisateurs peuvent modifier en toute sécurité pour personnaliser
   le comportement de W&amp;B en fonction de leurs besoins spécifiques.
2. Paramètres internes : paramètres préfixés par « x&#95; » qui gèrent le comportement du SDK à bas niveau.
   Ces paramètres sont principalement destinés à un usage interne et au débogage. Bien qu&#39;ils puissent être modifiés,
   ils ne sont pas considérés comme faisant partie de l&#39;API publique et peuvent changer sans préavis dans les futures
   versions.
3. Paramètres calculés : paramètres en lecture seule automatiquement dérivés d&#39;autres paramètres ou
   de l&#39;environnement.

Les paramètres sont chargés à partir de plusieurs sources. Lorsqu&#39;un même paramètre est fourni
par plusieurs sources, celle qui apparaît le plus bas dans la liste l&#39;emporte. Par ordre de
priorité croissante :

1. Les valeurs par défaut définies sur ce modèle `Settings`.
2. Les fichiers de configuration (`~/.config/wandb/settings`, ou le fichier `settings` dans
   le répertoire désigné par la variable d&#39;environnement `WANDB_CONFIG_DIR`).
3. Les variables d&#39;environnement (celles préfixées par `WANDB_`, par ex. `WANDB_MODE`).
4. Les valeurs détectées à partir de l&#39;environnement d&#39;exécution, telles que le nom d&#39;hôte, le
   chemin du programme/script en cours d&#39;exécution, l&#39;exécutable Python, l&#39;image Docker et
   les détails du notebook Jupyter.
5. Les paramètres SageMaker, lors d&#39;une exécution dans un environnement Amazon SageMaker.
6. Le paramètre `settings` de `wandb.setup()`.
7. Le paramètre `settings` de `wandb.init()`.
8. Certains paramètres de `wandb.init()` (par exemple, `mode=` redéfinit le
   paramètre `mode`).

<ResponseField name="allow_media_symlink" type="bool">
  Indique si des liens symboliques vers les fichiers multimédias doivent être créés dans le répertoire du run.

  Si la valeur est true, les fichiers multimédias seront liés au répertoire du run par des liens symboliques ou physiques au lieu d’être copiés. Cela peut accélérer la journalisation et réduire l’utilisation du disque. Toutefois, toute suppression ou modification des fichiers d’origine avant leur téléversement vers le serveur W&amp;B sera répercutée dans les données téléversées.
</ResponseField>

<ResponseField name="allow_offline_artifacts" type="bool">
  Indicateur permettant de synchroniser les artefacts de tableau en mode hors ligne.

  Pour revenir à l’ancien comportement, définissez cette valeur sur False.
</ResponseField>

<ResponseField name="allow_val_change" type="bool">
  Indicateur permettant de modifier les valeurs de `Config` après leur définition.
</ResponseField>

<ResponseField name="anonymous" type="object">
  Obsolète et sera supprimé.
</ResponseField>

<ResponseField name="api_key" type="str | None">
  La clé API W&amp;B.
</ResponseField>

<ResponseField name="azure_account_url_to_access_key" type="dict[str, str] | None">
  Mappage des URL de comptes Azure vers leurs clés d’accès correspondantes pour l’intégration Azure.
</ResponseField>

<ResponseField name="app_url_override" type="str | None">
  Redéfinition de l’URL « app » pour l’interface W&amp;B.

  L’`app_url` est normalement calculée à partir de `base_url`, mais cette option permet de la définir explicitement.

  WANDB&#95;APP&#95;URL est la variable d’environnement correspondante.
</ResponseField>

<ResponseField name="base_url" type="str">
  L’URL du backend W&amp;B pour la synchronisation des données.
</ResponseField>

<ResponseField name="code_dir" type="str | None">
  Répertoire contenant le code à suivre par W&amp;B.
</ResponseField>

<ResponseField name="config_paths" type="collections.abc.Sequence[str] | None">
  Chemins des fichiers à partir desquels charger la configuration dans l’objet `Config`.
</ResponseField>

<ResponseField name="console" type="Literal">
  Le type de capture de console à appliquer.

  Les valeurs possibles sont :

  * &quot;auto&quot; - Sélectionne automatiquement la méthode de capture de console selon l’environnement et les paramètres du système.
  * &quot;off&quot; - Désactive la capture de console.
  * &quot;redirect&quot; - Redirige les descripteurs de fichiers de bas niveau pour capturer la sortie.
  * &quot;wrap&quot; - Redéfinit les méthodes d’écriture de sys.stdout/sys.stderr. Est mappé vers &quot;wrap&#95;raw&quot; ou &quot;wrap&#95;emu&quot; selon l’état du système.
  * &quot;wrap&#95;raw&quot; - Identique à &quot;wrap&quot;, mais capture directement la sortie brute au lieu de passer par un émulateur. Dérivé du paramètre `wrap` et ne doit pas être défini manuellement.
  * &quot;wrap&#95;emu&quot; - Identique à &quot;wrap&quot;, mais capture la sortie via un émulateur. Dérivé du paramètre `wrap` et ne doit pas être défini manuellement.
</ResponseField>

<ResponseField name="console_multipart" type="bool">
  Active la journalisation de console multipart.

  Lorsque la valeur est True, le SDK écrit la sortie de la console dans des fichiers horodatés sous le répertoire `logs/` au lieu d’un unique fichier `output.log`.

  Chaque partie est téléversée dès sa fermeture, offrant aux utilisateurs un accès aux journaux en temps réel pendant que le run est actif. La fréquence de rotation est contrôlée par `console_chunk_max_bytes` et/ou `console_chunk_max_seconds`. Si les deux limites sont définies sur `0`, tous les journaux sont téléversés à la fin du run.

  Remarque : les fragments téléversés sont immuables ; les séquences de contrôle du terminal qui modifient les lignes précédentes (par ex., les barres de progression utilisant des retours chariot) n’affectent que le fragment actuel.
</ResponseField>

<ResponseField name="console_chunk_max_bytes" type="int">
  Seuil de rotation basé sur la taille pour les journaux de console multipart, en octets.

  Démarre un nouveau fichier journal de console lorsque la partie actuelle atteint cette taille. N’a d’effet que lorsque `console_multipart` est `True`. Peut être combiné avec `console_chunk_max_seconds` ; la première limite atteinte déclenche la rotation. Une valeur de `0` désactive la limite basée sur la taille.
</ResponseField>

<ResponseField name="console_chunk_max_seconds" type="int">
  Seuil de rotation basé sur le temps pour les journaux de console multipart, en secondes.

  Démarre un nouveau fichier journal de console après l’écoulement de ce nombre de secondes depuis le début de la partie actuelle. Nécessite que `console_multipart` soit `True`. Peut être utilisé avec `console_chunk_max_bytes` ; la première limite atteinte ferme la partie. Une valeur de `0` désactive la limite basée sur le temps.
</ResponseField>

<ResponseField name="capture_loggers" type="dict[str, str] | None">
  Noms des loggers Python à capturer dans l’onglet Logs du run.

  Mappage entre les noms de loggers et les niveaux de journalisation minimaux. Lorsque ce paramètre est défini, wandb installe un
  logging.Handler sur chaque logger nommé et le supprime à la fin du run.
  Les enregistrements émis par ces loggers sont publiés dans le run en tant que sortie de console,
  de manière similaire à la capture de stdout/stderr.

  Les enregistrements sont formatés comme avec `logging.basicConfig()`, par exemple
  `INFO:my_module:Some message.` Ce format n’est actuellement pas personnalisable.

  Pour capturer tous les journaux, transmettez le nom du logger racine, à savoir &#39;root&#39;.

  Ce paramètre est indépendant du paramètre `console` : les deux peuvent être actifs
  simultanément.

  Exemple :

  ```python
  wandb.init(
      settings=wandb.Settings(
          console="off",
          capture_loggers={
              "my_app": "INFO",
              "my_app.training": "ERROR",
          },
      ),
  )
  ```
</ResponseField>

<ResponseField name="finish_timeout" type="float">
  Durée, en secondes, pendant laquelle attendre le téléversement des données à la fin d’une exécution.

  La définition de cette valeur peut limiter les coûts liés aux téléversements lents vers W&amp;B à la fin d’une
  exécution, mais l’exécution sera alors marquée comme plantée et certaines données pourraient
  être manquantes. Par défaut, `run.finish()` bloque jusqu’à ce que toutes les
  données soient téléversées.

  Si cette valeur est supérieure à zéro, W&amp;B abandonne le téléversement des
  données d’une exécution après ce nombre de secondes à la fin de celle-ci, ce qui libère votre
  script. Après un certain temps, l’exécution passe à l’état Crashed ou Failed dans l’interface utilisateur. Toutes les
  données non téléversées restent stockées sur le disque et peuvent être téléversées avec `wandb
  sync`.

  Utilisez le paramètre `finish_timeout_raises` pour lever une erreur en plus
  d’afficher un message d’avertissement.

  Les exécutions arrêtées par `wandb.teardown()` (qui s’exécute automatiquement à la fin
  d’un script via un hook atexit) respectent également ce paramètre.
</ResponseField>

<ResponseField name="finish_timeout_raises" type="bool">
  Indique s’il faut lever une TimeoutError si le délai `finish_timeout` expire.

  L’utilisation de ce paramètre avec `finish_timeout` entraîne la levée d’une TimeoutError par `run.finish()`
  à l’expiration du délai, en plus de l’affichage d’un message.

  Notez que `run.finish()` est appelé implicitement lorsqu’une Run est utilisée comme gestionnaire
  de contexte :

  with wandb.init() as run:
  ...  # run.finish() s’exécute à la fin du bloc `with`

  Cela ne provoque pas la levée d’une erreur par `wandb.teardown()` (puisqu’il s’exécute
  de toute façon à la fin d’un script).
</ResponseField>

<ResponseField name="insecure_disable_ssl" type="bool">

</ResponseField>

<ResponseField name="reinit" type="Union">
  Action à effectuer lorsque `wandb.init()` est appelé alors qu’une exécution est active.

  Options :

  * &quot;default&quot; : Utiliser &quot;finish&#95;previous&quot; dans les notebooks et &quot;return&#95;previous&quot;
    dans les autres cas.
  * &quot;return&#95;previous&quot; : Renvoyer l’exécution créée la plus récemment
    qui n’est pas encore terminée. Cela ne met pas à jour `wandb.run` ; voir
    l’option &quot;create&#95;new&quot;.
  * &quot;finish&#95;previous&quot; : Terminer toutes les exécutions actives, puis renvoyer une nouvelle exécution.
  * &quot;create&#95;new&quot; : Créer une nouvelle exécution sans modifier les autres exécutions actives.
    Ne met pas à jour `wandb.run` ni les fonctions de premier niveau comme `wandb.log`.
    Par conséquent, certaines intégrations plus anciennes qui dépendent de l’exécution globale
    ne fonctionneront pas.

  Peut également être une valeur booléenne, mais cette utilisation est obsolète. False équivaut à
  &quot;return&#95;previous&quot; et True équivaut à &quot;finish&#95;previous&quot;.
